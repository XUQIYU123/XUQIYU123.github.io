一、CubeMX + FreeRTOS 核心配置：SysTick 时基问题

在使用 STM32CubeMX 配合 FreeRTOS 开发时，SysTick 时基分配是一个需要重点关注的问题。

如果 HAL 库和 FreeRTOS 都按照默认配置使用 SysTick，就需要正确处理两者的时基管理，否则可能出现 HAL 延时异常、系统节拍不准确以及任务调度异常等问题。

1.1 SysTick 冲突的原因

首先需要了解两者分别使用 SysTick 做什么。

HAL 库默认使用 SysTick 作为 HAL 时间基准，通常用于：

  • HAL_Delay() 延时函数。
  • HAL 库内部的超时计时。
  • HAL_GetTick() 获取系统毫秒计数。

FreeRTOS 默认也可以使用 SysTick 作为系统节拍定时器，主要负责：

  • 维护系统 Tick 计数。
  • 更新任务延时状态。
  • 触发任务调度。
  • 实现基于 Tick 的时间管理。

因此，两者都需要维护各自的时间基准。如果没有正确处理 SysTick 中断和优先级，就可能导致 HAL 时基与 RTOS 时基之间出现问题。

1.2 推荐解决方案：分离 HAL 时基和 RTOS 时基

在实际工程中，一种常见做法是：

  • FreeRTOS 使用 SysTick 作为系统节拍。
  • HAL 库使用独立的 TIM 定时器作为 HAL 时间基准。

例如，可以根据芯片资源选择 TIM2、TIM3、TIM4 等定时器。这样可以让 HAL 库和 FreeRTOS 分别维护自己的时基，减少中断管理上的耦合。

整个配置与验证流程如下：

    flowchart TD
    S["CubeMX 新建 FreeRTOS 工程"] --> Q{"HAL 与 FreeRTOS<br/>是否都使用 SysTick?"}

    Q -->|"是（默认配置）"| R["同一个 SysTick 被两套时基共用"]
    R --> R1["HAL_Delay / HAL_GetTick 与 RTOS Tick 相互耦合"]
    R1 --> R2["可能出现延时不准、节拍异常、调度异常"]

    Q -->|"否"| OK["两者各自拥有独立时基"]

    R2 --> F["把 HAL 时基切换到独立 TIM<br/>TIM2 / TIM3 / TIM4 等"]
    F --> F1["确认定时器实际输入时钟<br/>HCLK / PCLK1 / PCLK2"]
    F1 --> F2["计算 PSC 与 ARR，得到 1ms 计数"]
    F2 --> F3["检查生成的 TIM 初始化代码<br/>与中断处理函数"]
    F3 --> V["编译下载，验证 HAL_Delay 与任务延时"]

    OK --> V
    V --> W["测量实际延时精度<br/>必要时调整 PSC / ARR"]

需要注意：

  • 定时器的具体选择需要结合 MCU 型号。
  • STM32 不同系列的定时器资源并不完全相同。
  • TIM1、TIM8 属于高级控制定时器，通常需要优先考虑电机控制、互补 PWM 等应用，但并不是绝对不能用作 HAL 时基。
  • 修改 HAL 时基后，需要确认 CubeMX 生成的定时器初始化代码、中断处理函数和 HAL 时间基准配置是否正确。

1.3 时钟配置检查

修改时基后，还需要重新检查时钟配置，重点关注：

  • HCLK：AHB 总线时钟。
  • PCLK1：APB1 总线时钟。
  • PCLK2：APB2 总线时钟。
  • TIM 定时器实际输入时钟。
  • 定时器预分频值 PSC 和自动重装载值 ARR。

特别注意：在 STM32 中，部分定时器的时钟频率与 APB 总线时钟并不总是相同。当 APB 预分频系数大于 1 时，部分系列的定时器时钟会变为 APB 时钟的 2 倍，具体需要查看对应芯片参考手册。

本节总结：HAL 库与 FreeRTOS 的时基需要合理分配。将 HAL 时基切换到独立 TIM 定时器，是一种常见且便于管理的工程方案，但不是唯一方案。

二、FreeRTOS 三种任务创建方式详解

FreeRTOS 本身提供了动态任务和静态任务创建接口。在 STM32CubeMX 中使用 FreeRTOS 时，还经常会接触到 CMSIS-RTOS2 封装接口。

这三种方式的主要区别在于接口层级和内存管理方式。

2.1 xTaskCreate：动态任务创建

核心原理

xTaskCreate() 是 FreeRTOS 原生任务创建函数。调用该函数时，FreeRTOS 会从自己的堆内存中动态申请任务所需的内存空间，主要包括：

  • TCB（Task Control Block）：任务控制块。
  • Stack：任务栈空间。

TCB 中保存任务运行所需要的信息，例如任务优先级、任务栈指针、任务状态等。任务栈则用于保存任务运行过程中的局部变量、函数调用信息和上下文等。

需要注意，动态内存管理并不意味着一定会产生内存碎片，具体取决于使用的 Heap 实现。例如：

  • heap_1：只分配，不支持释放。

  • heap_5：支持多个不连续内存区域，并具有合并空闲块的能力。

因此，动态任务适合开发灵活、资源需求变化较多的项目，但需要关注堆空间大小和内存分配失败的问题。

与动态任务创建不同，xTaskCreateStatic() 不会从 FreeRTOS 堆中申请任务的 TCB 和栈空间。这两部分内存需要由开发者提前定义。

  • 工业控制设备。

  • 不希望任务运行过程中动态申请内存的项目。

2.3 osThreadNew：CMSIS-RTOS2 任务创建

很多初学者容易把 osThreadNew() 当成 FreeRTOS 原生 API。实际上，它属于 ARM CMSIS-RTOS2 标准接口。

CMSIS-RTOS2 提供了一套统一的 RTOS API，让上层应用能够通过标准接口使用不同的 RTOS 内核。在 STM32CubeMX 中，如果选择 CMSIS-RTOS2 适配方式，通常可以使用 osThreadNew() 创建任务。

具体使用动态还是静态创建，需要结合 CMSIS 适配层实现以及线程属性中的内存配置判断，不能简单地认为所有情况下都调用 xTaskCreate()。

优点

  • 遵循统一的 RTOS 接口标准。
  • 提高上层应用代码的可移植性。
  • 降低业务代码与具体 RTOS 内核之间的耦合。

缺点

  • 增加了一层 API 封装。
  • 某些 FreeRTOS 特有功能需要通过原生 API 实现。
  • 不同 RTOS 的功能和行为并非完全一致，因此更换内核时仍然可能需要修改代码。

三、FreeRTOS 多任务调度核心机制与常见问题

多任务并不意味着多个任务可以在单核 MCU 上真正同时执行。对于 STM32 这类单核 MCU，FreeRTOS 主要通过任务调度，在不同任务之间分配 CPU 执行时间。

3.1 优先级抢占式调度

FreeRTOS 支持优先级抢占式调度。在开启抢占式调度的情况下，调度器会优先选择当前处于就绪状态且优先级最高的任务运行。

例如，假设系统中有三个任务：

任务 优先级 状态
Task1 3 就绪
Task2 2 就绪
Task3 1 就绪

当调度器运行时：

  1. 首先执行优先级最高的 Task1。
  2. 如果 Task1 进入阻塞状态，调度器会选择 Task2。
  3. 如果 Task2 也进入阻塞状态，则执行 Task3。
  4. 当 Task1 再次进入就绪状态时，在抢占式调度下，它可以抢占正在运行的低优先级任务。

任务状态之间的迁移关系如下：

    stateDiagram-v2
    state "就绪 Ready" as Ready
    state "运行 Running" as Run
    state "阻塞 Blocked" as Block
    state "挂起 Suspended" as Susp

    [*] --> Ready

    Ready --> Run: 调度器选中（当前最高优先级就绪任务）
    Run --> Ready: 被更高优先级任务抢占 / 时间片用完
    Run --> Block: vTaskDelay / 等队列 / 等信号量 / 等事件组
    Block --> Ready: 延时到期 / 等待的事件满足
    Ready --> Susp: vTaskSuspend()
    Run --> Susp: vTaskSuspend()
    Block --> Susp: vTaskSuspend()
    Susp --> Ready: vTaskResume()
    Run --> [*]: vTaskDelete()

3.2 高优先级任务为什么会导致系统卡死

这是 FreeRTOS 初学者非常容易遇到的问题。

假设 Task1 的优先级高于 Task2。当 Task1 一直处于运行状态，且没有任何阻塞或主动让出 CPU 的操作时，调度器就没有机会让 Task2 正常运行，这会导致低优先级任务长期得不到 CPU 时间。

注意：如果开启时间片调度，同优先级任务之间还可以轮流运行，但不会因此自动让低优先级任务获得执行机会。

    flowchart LR
    T1["Task1<br/>优先级 3<br/>while(1) 无阻塞"] -->|"持续占用 CPU"| CPU["CPU 执行时间"]
    CPU -->|"永远轮不到"| T2["Task2<br/>优先级 2"]
    T2 --> R["现象：Task2 不执行<br/>看起来像系统卡死"]

3.3 任务如何主动释放 CPU

FreeRTOS 提供了多种方式，让任务进入阻塞状态或主动让出 CPU。

1. vTaskDelay()

让当前任务阻塞指定的 Tick 时间。

这里的 pdMS_TO_TICKS(1000) 表示将 1000ms 转换成对应的系统 Tick 数量。

需要注意，vTaskDelay() 是相对延时，任务的实际循环周期还会受到任务执行时间影响。如果需要更加稳定的周期性执行，可以使用 vTaskDelayUntil()。

2. 队列等待

当队列中没有数据时，任务可以进入阻塞状态，等待其他任务发送数据。

3. 信号量等待

任务可以等待信号量，当信号量不可用时进入阻塞状态。

4. 事件组等待

任务可以等待指定事件位满足条件后再继续执行。

这些阻塞式 API 可以让 CPU 去执行其他就绪任务，而不是让任务一直空转。

    flowchart TD
    A["任务进入 while(1)"] --> B{"本轮是否还有事可做?"}
    B -->|"有"| C["执行本轮逻辑"]
    C --> A
    B -->|"没有"| D["调用阻塞 API"]
    D --> D1["vTaskDelay / vTaskDelayUntil"]
    D --> D2["xQueueReceive 等数据"]
    D --> D3["xSemaphoreTake 等信号量"]
    D --> D4["等事件组位"]
    D1 --> E["任务进入阻塞态<br/>调度器切到其他就绪任务"]
    D2 --> E
    D3 --> E
    D4 --> E
    E --> F["条件满足后回到就绪态"]
    F --> A

3.4 FreeRTOS 常见系统异常原因

除了高优先级任务长期占用 CPU，还有以下问题需要注意：

  1. 任务死锁：多个任务等待彼此持有的资源，导致都无法继续执行。
  2. 资源互锁：多个任务同时访问共享资源，却没有正确使用互斥锁、临界区等同步机制。
  3. 中断服务函数执行时间过长：中断服务函数（ISR）应尽量保持简短。耗时较长的处理工作建议交给任务完成，必要时通过队列、信号量等方式通知任务。
  4. 中断优先级配置错误：FreeRTOS 对中断优先级有一定要求。特别是使用 FromISR 系列 API 时，需要确保中断优先级符合 configMAX_SYSCALL_INTERRUPT_PRIORITY 等配置要求。
  5. 任务栈溢出：任务栈空间不足，可能导致内存被破坏，出现程序跑飞、HardFault 等问题。建议合理设置任务栈大小，并根据项目需要开启 FreeRTOS 栈溢出检测。

遇到异常时，可以按下面的顺序排查：

    flowchart TD
    A["系统表现为卡死 / 无响应"] --> B{"高优先级任务是否在<br/>while(1) 中长期不阻塞?"}

    B -->|"是"| B1["低优先级任务拿不到 CPU"]
    B1 --> B2["加 vTaskDelay / vTaskDelayUntil"]
    B2 --> B3["或用队列 / 信号量 / 事件组等待"]

    B -->|"否"| C{"多个任务是否互相等待<br/>对方持有的资源?"}
    C -->|"是"| C1["死锁 / 资源互锁"]
    C1 --> C2["统一加锁顺序，等待加超时<br/>共享资源用互斥量或临界区保护"]

    C -->|"否"| D{"ISR 是否过长，<br/>或中断优先级配置越界?"}
    D -->|"是"| D1["ISR 只做通知，重活交给任务"]
    D1 --> D2["核对 configMAX_SYSCALL_INTERRUPT_PRIORITY<br/>逻辑中断优先级数值要更大"]

    D -->|"否"| E{"是否出现 HardFault / 程序跑飞?"}
    E -->|"是"| E1["开启栈溢出检测<br/>检查任务栈大小、数组越界、野指针"]
    E -->|"否"| F["用调试器查看各任务状态<br/>与栈高水位，定位阻塞点"]

本节总结：FreeRTOS 的多任务调度并不是让多个任务同时运行，而是通过任务状态、优先级和调度机制分配 CPU 时间。编写任务时，应避免无意义的无限空转，合理使用延时、队列、信号量和事件组等阻塞机制。

4.2 Cortex-M 核心寄存器

Cortex-M 内核有一组非常重要的核心寄存器。首先需要区分：

  • R0～R15：共 16 个核心通用寄存器编号。
  • xPSR：程序状态寄存器，属于特殊寄存器，不属于 R0～R15。
    flowchart TD
    CM["Cortex-M 核心寄存器"] --> G["R0 - R12<br/>通用寄存器"]
    CM --> SP["R13 SP<br/>栈指针"]
    CM --> LR["R14 LR<br/>链接寄存器"]
    CM --> PC["R15 PC<br/>程序计数器"]
    CM --> PS["xPSR<br/>程序状态寄存器"]

    G --> G1["R0 - R3<br/>函数参数 / 返回值"]
    G --> G2["R4 - R11<br/>跨函数调用需要保留"]
    G --> G3["R12<br/>临时寄存器"]

    SP --> SP1["MSP 主栈指针"]
    SP --> SP2["PSP 进程栈指针"]

    PS --> P1["APSR<br/>运算状态标志"]
    PS --> P2["IPSR<br/>异常编号"]
    PS --> P3["EPSR<br/>执行状态"]

1. R0～R12：通用寄存器

主要用于存储临时数据、函数参数和运算结果。在 ARM 调用约定中：

  • R0～R3：通常用于传递函数参数和返回值。
  • R4～R11：通常用于保存需要跨函数调用保留的数据。
  • R12：通常作为临时寄存器使用。

2. R13：SP（Stack Pointer）栈指针

用于指向当前使用的栈空间。Cortex-M 支持两种栈指针：

  • MSP：主栈指针。
  • PSP：进程栈指针。

在典型的 FreeRTOS Cortex-M 应用中：

  • 中断处理通常使用 MSP。
  • 普通任务通常使用 PSP。

具体行为还与处理器运行模式和系统配置有关。

3. R14：LR（Link Register）链接寄存器

主要保存函数调用时的返回地址。当 CPU 执行 BL 函数调用指令时，会将返回信息保存到 LR 中。函数执行结束后，可以通过 LR 返回调用位置。

    flowchart LR
    A["主函数执行到 BL Function"] --> B["LR 保存返回地址"]
    B --> C["跳转到 Function 执行"]
    C --> D["执行完 BX LR"]
    D --> E["回到主函数的下一条指令"]

4. R15：PC（Program Counter）程序计数器

程序计数器，用于控制 CPU 下一步执行的位置。CPU 根据 PC 指向的指令地址获取指令，并按照程序执行流程更新 PC。

5. xPSR：程序状态寄存器

xPSR 用于保存处理器的状态信息，主要包括：

  • APSR：应用程序状态寄存器，保存运算状态标志。
  • IPSR：中断程序状态寄存器，保存当前异常编号。
  • EPSR：执行程序状态寄存器，包含执行状态相关信息。

其中，APSR 中常见的状态标志有：

标志位 含义
N 负数标志
Z 零标志
C 进位标志
V 溢出标志

这些标志位会影响后续条件执行和条件跳转。

4.3 常用 ARM 汇编指令

下面介绍一些 Cortex-M 汇编中经常接触到的指令。

1. LDR / LDRB：从内存读取数据

LDR 用于从内存中读取一个字（通常为 32 位），并将数据存入寄存器。

含义：读取地址 R1 + 4 处的数据，存入 R0。

LDRB 则用于读取一个字节（8 位）。

读取 R1 指向地址的一个字节，并将其零扩展后存入 R0。

2. STR / STRB：将寄存器数据写入内存

STR 用于将寄存器中的一个字（通常为 32 位）写入内存。

含义：将 R0 中的数据写入 R1 + 4 对应的内存地址。

STRB 则用于写入一个字节。

只将 R0 的低 8 位写入内存。

5. B / BL：跳转指令

B：无条件跳转。

BL：带链接的跳转指令，常用于函数调用。

6. MOV / MOVS：数据传送指令

MOV 用于将数据从一个寄存器复制到另一个寄存器，或者在支持的指令形式中加载立即数。

含义：将 R4 的数据复制到 R0。

MOVS 则会更新相关状态标志位。

将立即数 1 写入 R1，并更新状态标志。

7. PUSH / POP：栈操作指令

PUSH 用于将寄存器中的数据保存到栈中。

POP 用于从栈中恢复之前保存的数据。

主要作用：

  • 保存函数调用过程中需要保留的数据。
  • 保护寄存器中的重要内容。
  • 保存和恢复程序执行上下文。

五、STM32 栈空间工作机制

栈（Stack）是 MCU 内存管理中非常重要的一部分。在学习函数调用、局部变量、任务切换和中断处理时，都会接触到栈。

5.1 什么是满递减栈

在典型的 Cortex-M STM32 开发环境中，栈通常采用**满递减（Full Descending）**方式。它包含两个概念：

1. 递减（Descending）

栈指针 SP 随着数据压入栈中，向更小的内存地址移动：

2. 满栈（Full）

SP 指向当前栈顶已经存放数据的位置。

因此，满递减栈的特点是：

  • 压栈时，SP 先递减，再存入数据。
  • 出栈时，先读取 SP 指向的数据，再递增 SP。

    A --> C["满：SP 指向最后一个已压入的数据"]
    B --> D["PUSH：SP 先减，再存"]
    C --> E["POP：先读，SP 再增"]

5.4 栈与 FreeRTOS 的关系

在裸机程序中，通常主要使用主栈空间。而在 FreeRTOS 中，每个任务都有自己独立的任务栈。

    flowchart TD
    RTOS["FreeRTOS 栈布局"] --> T1["Task1 任务栈<br/>局部变量 / 调用栈 / 上下文"]
    RTOS --> T2["Task2 任务栈"]
    RTOS --> T3["Task3 任务栈"]
    RTOS --> MSP["MSP 主栈<br/>中断与异常处理使用"]
    T1 --> SW["任务切换"]
    SW --> S1["保存当前任务的寄存器上下文"]
    S1 --> S2["切换到下一个任务的栈指针 PSP"]
    S2 --> S3["恢复下一个任务的寄存器上下文"]

每个任务在运行时，都需要自己的栈空间来保存局部变量、函数调用信息以及任务上下文。当任务发生切换时，FreeRTOS 需要保存当前任务的上下文，并恢复下一个任务的上下文。

这也是为什么理解 SP、LR、寄存器和 PUSH/POP 指令，对理解 RTOS 任务切换机制非常重要。

六、总结与学习收获

通过近期的学习，对 FreeRTOS 和 ARM Cortex-M 内核有了进一步认识。本次主要掌握了以下知识：

  1. FreeRTOS 工程配置：理解了 HAL 库与 FreeRTOS 的时基分配问题，知道可以通过独立 TIM 定时器管理 HAL 时基，降低 SysTick 的耦合。
  2. FreeRTOS 任务创建：理解了动态任务、静态任务以及 CMSIS-RTOS2 接口之间的区别，初步掌握了不同任务创建方式的内存管理原理。
  3. 多任务调度：理解了优先级抢占式调度机制，知道高优先级任务如果一直运行且不进入阻塞状态，可能导致低优先级任务无法获得 CPU 时间。
  4. ARM Cortex-M 汇编基础：认识了 R0～R15、SP、LR、PC 和 xPSR，了解了 LDR、STR、ADD、SUB、CMP、B、BL、PUSH、POP 等常用指令。
  5. 栈空间管理：理解了满递减栈的基本工作方式，以及 FreeRTOS 中每个任务拥有独立栈空间的设计。
